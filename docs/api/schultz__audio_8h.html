Detailed Description

Sound out and microphone in.

Part of the host facing interface. A host binds to schultz_api.h, which includes this header.

Audio stands on its own. It is not part of a window, because everything else the toolkit owns has a lifetime tied to something on screen and sound does not: a tool with no window may still want to make one, a phone carries on playing while the window is in the background, and a machine with two windows still has one set of speakers.

The host gives bytes, and the toolkit never asks for them

SDL will call an application back on its audio thread when it wants more data. Nothing here does that. A host writes a chunk when it has one and asks how much is still unplayed, which is the same loop in C and in a language with a garbage collector, and which never puts a host's code on a realtime thread:

if (schultz_audio_stream_queued(audio, stream) < want) {
schultz_audio_stream_write(audio, stream, bytes, length);
}
schultz_audio_stream_queued
uint64_t schultz_audio_stream_queued(const schultz_audio *audio, schultz_handle stream)
Returns how many bytes are waiting to be played.
schultz_audio_stream_write
int32_t schultz_audio_stream_write(schultz_audio *audio, schultz_handle stream, const void *bytes, uint64_t length)
Hands the stream more samples.

Recording is the same rule the other way round: the toolkit holds what the microphone produced and the host reads it when it likes.

Decodes a sound and keeps it, ready to play.

For anything short and played often: a click, an alert, a chime. It is decoded now rather than while it plays, because a sound decoded again on every press is work done twice for nothing.

WAV, AIFF, VOC and AU, plus MP3, FLAC and Ogg Vorbis. What is deliberately absent is MOD, MIDI and the console formats, whose decoders are copyleft or need a set of instruments shipped with them; see THIRD_PARTY_NOTICES.md.

Parameters
audioThe system. Must not be NULL.
pathThe file. Must not be NULL.
out_soundReceives the sound. Must not be NULL.
Returns
SCHULTZ_OK, SCHULTZ_ERR_INVALID_ARGUMENT, SCHULTZ_ERR_OUT_OF_MEMORY, SCHULTZ_ERR_UNREADABLE when the file is missing or is not something this build decodes, or SCHULTZ_ERR_UNAVAILABLE when no device would open.

◆ schultz_audio_stream_queued()

uint64_t schultz_audio_stream_queued ( const schultz_audio *  audio,
schultz_handle  stream 
)

Returns how many bytes are waiting to be played.

Counted as they were written, in the format the stream was created with, because nothing is converted until the device asks for it. So a stream written at 22050 and played at 48000 reports what was written, and dividing by the rate, the channel count and the sample size gives how many seconds of sound are still to come. That is what makes this usable as a clock as well as for deciding when to write more.

Parameters
audioThe system. NULL yields zero.
streamA stream from schultz_audio_stream_create.
Returns
Bytes not yet played.

Opens an encoder: samples in, Opus packets out.

The sound half of recording rather than playing. Nothing here sends anything anywhere: the packets come back to the caller, which decides what they are for. A transport is a different problem.

Opus, because it is the audio codec that can be shipped without a patent licence and the best of them at the bitrates a call uses. It is already vendored for playback, so encoding adds nothing to the binary but the encoder itself.

Opens a decoder the host pushes an encoded file into, a piece at a time.

What internet radio wants. A stream takes samples and this takes the file itself – MP3, Ogg Vorbis, FLAC, WAV – in whatever chunks it arrives in, and works them out as it plays.

The rule is the same as everywhere else here: the host writes, and nothing calls the host back. The decoder reads from what has been written, on its own thread, and an empty buffer means "not yet" rather than "the end", so a station that is slow for a moment does not stop.

Writes what the microphone makes straight into a WAV file.

For recording rather than listening. The toolkit takes the samples as the device produces them and writes them out, so nothing has to be read on a clock and nothing is lost while an application is busy.

Saving and reading are two ways to the same bytes. While a recorder is saving, the toolkit drains it, so schultz_audio_recorder_read has nothing to give. An application picks one.

The file is a WAV of exactly what was asked for at schultz_audio_recorder_create. Its header is written when the file opens and corrected when it closes, so a file left behind by a crash still opens, with whatever had been written by then.
